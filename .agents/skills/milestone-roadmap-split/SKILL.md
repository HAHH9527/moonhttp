# 里程碑拆分入路线图

## 概述

把可行性报告 `proj-init-docs/okhttp-on-async-http/README.md` 中某里程碑（MN）的工作拆
分为工作包，写入 `docs/roadmap/MN/`；与原报告不符之处登记为差异（D 表），牵扯后续
里程碑的降级项登记为欠账（F 编号），用总/分两层 deferred-items 结构跨里程碑跟踪。
全程不改动 `proj-init-docs/`（冻结参考资料，永不回改）。

输入：`$ARGUMENTS` 为里程碑编号（如 `M2`）；缺省时先向用户确认目标里程碑。

## 前置阅读（拆分前必读）

1. 原报告该里程碑章节 + 涉及的各特性文档（`proj-init-docs/okhttp-on-async-http/` 下
   对应 folder）。
2. 项目宪法 `.specify/memory/constitution.md`（非侵入、验收先行、中文文档等
   不可妥协项）。
3. `.specify/` 的 spec 模板（包文档的 speckit 输入种子须与之对齐）。
4. `docs/roadmap/deferred-items.md` 总入口 + 相关 mN 明细——**前序里程碑的欠账可能
   正是本里程碑的输入需求**（如 M2 拆分必核对 M1 的 F1–F6）。
5. `moon.mod` 与 `src/` 骨架（包名建议与现状一致）。
6. 前序里程碑 roadmap（M1 先例：`docs/roadmap/M1/`，10 包结构）。

## 流程

### 1. 用里程碑人日算术核对范围

- 用原报告给该里程碑的人日做加法，核对列入范围的能力是否装得下。先例：M1≈16d
  （4.5+5+3+3.5），据此把代理与 DNS 缓存划归 M2。
- 装不下的能力一律裁剪出本里程碑，登记为差异并分诊（第 5 步）。

### 2. 定包

粒度判据——每个包：

- 能单独走一遍 `specify → clarify → plan → tasks → implement`；
- 有独立、可判定的验收判据（不依赖兄弟包同时在场）。

聚合判据——闸门同源、共享同一并发/决策闸口的功能并入同一包。先例：enqueue 并入
P09 Dispatcher（闸门在链首），避免先交付无并发控制的 API 再返工。

通用先例（M1 已验证）：

- 测试基建单列（P03：可控服务端/裸 TCP 夹具，宪法 IV：网络行为测试基于本地
  可控服务端）；
- 基准门禁收口单列（P10：场景矩阵 + 性能门禁）；
- 值对象/模型先行（P01/P02），执行骨架居中（P05），策略类（重定向/重试/超时）
  居后，最后收口。

依赖表述用**边表**（`X → Y` 列表）+ 拓扑分层表，不画 ASCII 图（易误读）。

按 M1 先例的 13 个标准小节：

<!-- US-1 …（P1/P2 优先级）；每条含场景与可判定验收 -->

### 4. 写里程碑 README.md

要素（M1 先例结构）：

1. 头部引言：来源、拆分说明、**不修改 proj-init-docs、执行以差异清单为准**的声明。
2. 目标与交付判据（沿用原报告口径）+ 人力口径（逐包加总 vs 原报告人日，差额
   须有解释；先例：M1 逐包 ≈17d vs 原 ~16d，差额为 P03 测试基建单列）。
3. 工作包清单表（包 | 名称 | 一句话范围 | 前置依赖 | 人力 | 主要来源章节）。
4. 依赖边表 + 拓扑分层表 + 建议实施顺序。
5. **差异清单 D 表**：每条含（# | 差异 | 原文出处 | 理由与处理），编号从 D1 递增；
   表前加指向 deferred-items 总入口与 mN 明细的交叉引用。
6. 补充口径说明（非差异的落地澄清，如「响应头顺序不可保真」这类验收注意）。
7. 「每包如何走 speckit」说明（Pxx 的 speckit 输入种子 → `/speckit-specify`）。

### 5. 差异分诊

把 D 表逐条分为两类：

- **MN 内部消化**：终态口径，不是欠账。先例：归属调整（enqueue 并入 P09）、
  测试夹具自建（是可复用资产）、非侵入边界内的收敛口径（L3 = 缓存折叠 Map）。
- **牵扯后续里程碑**：显式降级、须回补 → 编 F 号登记欠账。先例：M1 的 9 条差异
  中 6 条欠账集中 M2，其余分属 M3/M4/M5 与未排期。

### 6. 维护欠账总/分结构

**初次就建成两层结构，不要先建单文件再重构**（M1 曾先建 `m1-deferred-items.md`
单文件，被用户纠正为下列结构）：

- 明细 `docs/roadmap/deferred-items/deferred-items-mN.md`：本里程碑全量欠账，
  每条含（F# | 条目 | MN 降级口径 | 回补位置 | 回补要点 | 状态）。F 编号全局
  唯一、跨里程碑递增（沿用已有最大号续编）。
- 总入口 `docs/roadmap/deferred-items.md`：**只引用未完成条目**。含四节：接入
  约定、子文档索引（含后续里程碑占位行）、未完成条目汇总表、按里程碑速查。
- 在本里程碑 README 的 D 表处加交叉引用（总入口 + mN 明细）。
- 状态取值：待回补 / 已回补 / 裁定不做。
- 凡涉及上游仓库改动（侵入点 I1–I12，沿用原报告 §3 总表）的条目，标注
  **「须人工批准」**（宪法原则 I）。

### 7. 回补闭环（欠账后续维护）

用户要求回补或裁定某欠账时：

1. 明细文件中该条改状态：已回补（附 spec/commit 引用）或裁定不做（附理由）。
2. 从总入口移除该行，并同步更新「子文档索引」的未完成计数与「按里程碑速查」。
3. 若回补引入与原报告的新差异，按第 5 步在对应里程碑登记 D 表。

### 8. 收尾自检

- [ ] `proj-init-docs/` 零改动（git status 核验）；
- [ ] 人日加总与原报告口径核对，差额已解释；
- [ ] 交叉引用三处互链（总入口 ↔ mN 明细 ↔ 里程碑 README）路径拼写正确，
      防 `deferredred-` 类笔误；
- [ ] 只新增 `docs/roadmap/MN/` 与欠账文件，无其他文件被动；
- [ ] 涉上游侵入点的条目均标注「须人工批准」；
- [ ] 每包 target 矩阵按宪法标注。

## 硬约束（宪法，不可妥协）

- 只经公开 API 使用 `moonbitlang/async`，禁止 fork、复制或 vendor 上游源码；
  涉上游仓库改动或 issue/PR 提交，**必须事先获用户人工批准**。
- `proj-init-docs/` 冻结不改；执行以 roadmap 差异登记为准。
- 验收场景与测试先行；项目文档全部使用中文。
