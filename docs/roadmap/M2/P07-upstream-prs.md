## 功能描述（speckit 输入种子）

准备并向 `moonbitlang/async` 回馈三份高价值小改动（PR 材料完备、基准证据
齐备、文案就绪），提交动作在**人工批准后**执行：

- **I1 发送缓冲 1KB→16KB**（`send.mbt:85` 一处常量/参数化，~5 行）：修复
  上传路径 syscall 放大（1MB body ≈ 1024 次小段写）；证据 =
  M2-P06 实验分支对照数据。原报告 M2 范围内。
- **I2 DNS 缓存**（`connect_to_host` 内进程级缓存，~30 行）：全生态共享的
  解析缓存；证据 = M2-P02 自组版对照与基准。原报告 M2 范围内。
- **I5 Host 头覆盖**（`Client::connect` 允许覆盖 Host / `set_host?`，~5 行）：
  解锁 http-over-proxy absolute-form；M2 主分支不启用该能力（F14 跟踪），
  PR 材料随 F2 回补一并提供（差异 D4 扩入）。

## 范围

包含：

- 三份补丁（在上游本地副本上开发、自测，宪法技术约束的本地实验形态）。
- 每份 PR 的基准证据（I1 依 M2-P06 报告；I2 依 M2-P02/P06 数据；I5 附
  absolute-form 行为说明与重复 Host 头缺陷复现）。
- issue/PR 文案（问题陈述、修法、数据、兼容性说明）。
- **人工批准流程**：材料齐备后向项目所有者提交评审；批准前不发起任何
  issue/PR（宪法 I）。

非目标（显式排除）：

- I4（407 挑战回调，可选 PR）：M2 默认不做（M2-P05 绕行已闭环）；
- I6–I9、I10–I12（各自里程碑/未排期，侵入点总表既定）；
- 上游代码评审期间的反复修改承诺（协作成本独立估算，不占 M2 人日）；
- PR 合并后的主分支切换动作（I1→F16、I2→F15、I5→F14 各自跟踪）。

## 用户故事种子

### US-1 I1 PR 材料与提交（P1）

**独立测试**：材料评审清单 + 补丁在上游本地副本的自测。

**验收场景**：

1. 补丁 diff ≤ ~5 行且含参数化考量（clarify C2）；上游本地副本全测试通过。
2. 基准证据：100MB 上传 syscall 主分支 vs 16KB 补丁对照表（M2-P06 数据引用）。
3. PR 文案完整（问题/修法/数据/兼容性）；提交前有人工批准记录。

### US-2 I2 PR 材料与提交（P1）

**验收场景**：

1. 补丁 ~30 行：缓存结构、TTL 策略（min TTL 或默认 30s）、失效口径
   （clarify C3）；上游本地副本全测试通过。
2. 基准证据：新建连接场景解析往返消除的数据（对照 M2-P02 自组版口径）。
3. 提交前有人工批准记录；moonhttp 自组版在其合并前的并存说明写入文案。

### US-3 I5 PR 材料与提交（P2）

**验收场景**：

1. 补丁 ≤ ~5 行（Host 覆盖或 `set_host?` 形态，clarify C4）；含重复 Host 头
   缺陷的最小复现。
2. 文案说明该能力解锁的 http-over-proxy absolute-form 语义（RFC 9110 §7.2
   对齐动机）。
3. 提交前有人工批准记录；moonhttp 侧启用时点 = F14。

### US-4 批准流程合规（P1）

**验收场景**：

1. 批准前：仓库与上游均无本包发起的 issue/PR（git/网络核验）。
2. 批准后提交的内容与批准材料一致（无夹带改动）。

## 边界用例

- 上游 0.22.x 演进导致补丁基线漂移（rebase 记录）；
- PR 被拒/长期搁置：欠账 F14/F15/F16 转入「裁定不做」或维持待回补并注明
  （第 7 步回补闭环规则）；
- 补丁与 moonhttp 自组实现的语义分歧（I2 缓存键口径差异清单）。

## 需求种子

- **FR-001** 三份材料 MUST 各自独立可评审（补丁+数据+文案三件套）。
- **FR-002** 提交动作 MUST 在人工批准后执行；agent 不得自主发起（宪法 I）。
- **FR-003** 补丁 MUST 仅涉最小改动面（I1 ~5 行、I2 ~30 行、I5 ~5 行），
  不夹带其他变更。
- **FR-004** 本包不改动 moonhttp 主分支行为（材料在上游本地副本产出）。

## 关键设计要点

- I1 形态：常量扩为 16KB vs `Sender::new` 参数化/按首次大写入增长——
  上游口味优先（clarify C2），moonhttp 侧无偏好（L1 无绕行、必须上游）。
- I2 与 M2-P02 自组版的关系：自组版是合并前的 moonhttp 兜底与 PR 的对照
  实现；合并发版后评估退役自组版（F15）。
- I5 与 F2 的关系：PR 是 absolute-form 的前提，材料随本包出、能力启用
  单独跟踪（F14），避免「上游未合并导致 M2 判据悬空」。

## 侵入性与宪法合规

- 本包全部产出**涉上游仓库改动**：任何 issue/PR 提交必须事先人工批准
  （宪法原则 I；处理原则见原报告 §3：I1–I7 以 PR 回馈上游为目标）。
- 宪法 II：三份 PR 均为性能动机，证据数据必须完备（重点报告要求）。
- 本包对 moonhttp 主分支零侵入、零行为变化。

## 性能影响

- I1：上传 syscall ÷16（与 body 大小线性收益）。
- I2：新建连接场景省 getaddrinfo 往返（~100µs+）。
- I5：本身非性能项（语义解锁），无性能声明。

## 测试方案

- 补丁在上游本地副本跑上游全量测试；基准证据引用 M2-P02/P06 归档数据。
- moonhttp 侧无新测试（主分支零变化）；F14/F15/F16 的回补验收在各自条款。

## 澄清问题种子（clarify 输入）
